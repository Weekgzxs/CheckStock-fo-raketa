# CheckStock — где сейчас товар

Веб-прототип учёта остатков по складам фулфилмента (ФФ): остатки, резерв FBS, перемещения между ФФ,
отгрузки FBO/FBS, история операций. Стек: Python 3.13, FastAPI, PostgreSQL 17, psycopg 3, Jinja2
(серверный рендеринг, без JS-сборки).

## Запуск

Нужен только Docker.

```bash
docker compose up -d --build
```

Откройте http://localhost:8000. При первом старте база заполняется тестовыми данными из задания
(ФФ «Север» и «Юг», приходы SKU-101/102/103). Кнопка «Сбросить к тестовым данным» внизу главной
страницы возвращает их в любой момент.

## Проверки

```bash
docker compose run --rm app pytest -v
```

Тесты идут на настоящем PostgreSQL в отдельной базе `checkstock_test`, демо-данные они не трогают.
Каждый тест после действий проверяет сверку остатков (см. ниже). Покрыто:

### Ручной сквозной сценарий

1. **Остатки**: Север — SKU-101: 10, Юг — 6; сверка «✓ сходится».
2. **Операции → Заказ FBS**: Юг, SKU-101, 8 шт. → нехватка: «на Юге 6, по всем ФФ хватает: Север — 10».
   Предлагаются три выхода: разбить (6 с Юга + 2 с Севера), взять всё с Севера, переместить 2 шт. Север → Юг.
   Выберите «Разбить»: на главной два резерва, у SKU-101 доступно 8 из 16, в резерве 8.
3. Нажмите «Отгрузить клиенту» по резерву, затем ещё раз: второй раз — «уже обработан, повторно ничего не списано».
   Товар переходит в «FBS к клиенту».
4. **Перемещение** Север → Юг, SKU-102, 3 шт. → «В пути между ФФ», на Севере 2. «Принять на ФФ» → на Юге 3.
5. **Отгрузка FBO** с Юга, SKU-103, 2 шт. → «FBO в пути», «Принято складом МП» → «На складе МП».
6. **Склады ФФ → Удалить «Север»**: в подтверждении видно, сколько на нём числится. После удаления
   ФФ остаётся в остатках с пометкой «удалён», в истории — «ФФ удалён, остаток N шт.».
   Приход или заказ на него уже невозможен, а перемещение с него на Юг — возможно.
7. **История**: какой товар, сколько, откуда и куда — по каждому шагу.

## Ключевые решения

**Физический остаток хранится, транзит вычисляется.** Таблица `stock` хранит только то, что лежит на
полке ФФ: `on_hand` (физически) и `reserved` (резерв FBS); доступно = `on_hand − reserved`. Всё, что
в пути (между ФФ, FBO на склад МП, FBS к клиенту), — это сумма документов в соответствующем статусе.
Одно и то же количество нигде не записано дважды, поэтому транзит не может разойтись с документами.

**Сверка видна на экране.** Для каждого артикула:
`приход = на ФФ + в пути между ФФ + FBO в пути + на складе МП + FBS к клиенту`.
Колонка «Сверка» на главной и каждый тест проверяют это равенство после каждого действия.

**Документ = операция со статусом.** `docs.kind` / `docs.status`:

| Тип | Создание | Переходы |
|---|---|---|
| receipt (приход) | `done`, +on_hand | — |
| transfer | `in_transit`, −on_hand на ФФ отправки | → `received`, +on_hand на ФФ получения |
| fbs | `reserved`, +reserved (товар на полке, но заблокирован) | → `shipped`: −on_hand −reserved (едет к клиенту); → `cancelled`: −reserved |
| fbo | `in_transit`, −on_hand (товар покинул ФФ) | → `accepted` (на складе МП) |

**Повторное подтверждение не списывает дважды.** Переход статуса — один атомарный
`UPDATE docs SET status=new WHERE id=? AND status=required`. Если строка не обновилась, документ уже
обработан, и остатки не трогаются. Это работает и при двух одновременных запросах: второй ждёт блокировку
строки, а после коммита первого уже не находит нужный статус (`test_concurrent_confirm_writes_off_once`).

**Повторная отправка формы тоже.** В каждой форме есть скрытый `request_id` (UUID), в БД на нём
`UNIQUE` и `INSERT … ON CONFLICT DO NOTHING`. Двойной клик по «Оформить приход» создаёт один документ.
Части разбивки получают ключи `uuid5(request_id, i)`, вся разбивка — одна транзакция.

**Защита от отрицательных остатков на трёх уровнях.** Строка остатка блокируется (`SELECT … FOR UPDATE`)
перед проверкой доступного. В таблице есть `CHECK (on_hand >= 0, reserved >= 0, reserved <= on_hand)`.
Каждая HTTP-операция — одна транзакция: при любой ошибке откатывается целиком.

**Нехватка.** Если на выбранном ФФ доступного меньше, чем нужно, операция откатывается, и форма
показывает, где ещё есть товар. Если в сумме хватает, предлагается: разбить отгрузку (сначала выбранный
ФФ, потом ФФ с наибольшим доступным), взять всё с другого ФФ (если там хватает целиком) или создать
перемещение недостающего количества. Автоматически ничего не переносится: решение за менеджером.
Если не хватает и в сумме, это сообщается прямо.

**Удаление ФФ — мягкое (`deleted_at`).** Физически товар никуда не исчез, поэтому стирать его нельзя.
Удалённый ФФ:
- остаётся в «Остатках по ФФ» с пометкой «удалён», пока на нём что-то числится, а на странице складов видно, что именно;
- не принимает новых операций (приход, заказы, перемещения *на* него);
- позволяет вывезти остаток перемещением *с* него и завершить уже начатые операции (отгрузить
  или отменить резерв, принять перемещение, которое уже было в пути);
- в истории остаётся под тем именем, которое было в момент операции; имя можно занять новым ФФ.

**История** — журнал `history`: операция, артикул, количество, откуда, куда. Пишется в той же транзакции,
что и изменение остатков, поэтому журнал и остатки не расходятся.

**Почему без ORM.** Учёт — это несколько точных SQL-операций с блокировками и `ON CONFLICT`. В явном SQL
(psycopg 3) видно, что именно блокируется и списывается. Схема — один `schema.sql` (`CREATE … IF NOT
EXISTS` при старте); для прототипа миграции (Alembic) не нужны.

**Упрощения прототипа.** Один магазин, поэтому сущности «магазин» нет. Нет авторизации и пагинации
(история — последние 500 записей). Доставку FBS клиенту не отслеживаем: после отгрузки товар числится
«к клиенту». Приход проводится сразу, без статуса «ожидается».

## Структура

```
app/schema.sql      схема БД и ограничения
app/stock.py        вся логика учёта (операции, переходы, нехватка, разбивка, удаление ФФ, сводки)
app/main.py         HTTP-маршруты: одна операция = одна транзакция
app/templates/      4 экрана: Остатки, Операции, Склады ФФ, История
tests/              сценарии на реальном PostgreSQL
db/init.sql         создаёт тестовую базу
```

## ИИ в работе

Код писался с ИИ-ассистентом (Claude Code): он ускорил черновики SQL, шаблонов и тестов. Модель учёта
(что хранить, что вычислять), правила удаления ФФ и нехватки решены и проверены вручную. Тесты на
складских сценариях нашли реальную ошибку в сгенерированном коде: upsert с дельтой
(`INSERT … ON CONFLICT DO UPDATE SET on_hand = on_hand + EXCLUDED.on_hand`) падал на `CHECK`,
потому что PostgreSQL проверяет ограничения на предлагаемой строке вставки ещё до разрешения конфликта.
Исправлено на «создать строку, если её нет» + `UPDATE`.
